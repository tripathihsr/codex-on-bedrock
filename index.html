PROVISIONING BUNDLE · CODEX + AMAZON BEDROCK (INDIA)

Codex on Amazon Bedrock (India) — Installation & Architecture Guide

A small set of cross-platform scripts that connect OpenAI Codex to Amazon Bedrock in the India region, using a per-user Amazon Bedrock API key (bearer token) so model traffic is served in-country.

This document is technical reference material for setting up and operating the software. It describes design intent and configuration options; it is not a security certification, compliance attestation, or legal advice. Validate the setup against your own security, privacy, and regulatory requirements before production use.

00 Overview & Context

Development teams increasingly want a capable AI coding assistant such as Codex. One common path is a public-internet SaaS endpoint — which, for a regulated or public-sector organization, can mean source code, prompts, and proprietary context travel to an external vendor and potentially across regions. Where data residency is a requirement, that may be unacceptable.

This bundle configures Codex to run against Amazon Bedrock in the India region. OpenAI- compatible models (for example in.openai.gpt-5.6-terra) are served from Bedrock in ap-south-1 (Mumbai), with ap-south-2 (Hyderabad) as the in-country cross-Region destination — so teams can use the assistant without routing data to an external SaaS.

How this is designed to support data residency

  • In-country inference. Model calls go to the Bedrock endpoint in an India region, and the India geographic inference profile keeps routing within ap-south-1 / ap-south-2.
  • Your account, your controls. Everything runs in your AWS account under your IAM, logging (CloudTrail), and Bedrock invocation logs in the India regions.
  • Per-user identity. Each developer gets a dedicated low-privilege IAM user and their own credential, rather than a shared account-wide secret.
  • No external AI SaaS. Codex is pointed at the Bedrock runtime endpoint, not at a public model provider.

In short

Teams get a Bedrock-backed Codex experience configured to keep model traffic within the India region and your AWS account. Residency outcomes depend on your configuration and the AWS services' own regional behaviour — validate against your requirements.

Important — this direct setup is for validation / proof-of-concept

In this configuration, Codex connects directly to Amazon Bedrock using a per-user bearer token. The provisioning script creates a real IAM user and a long-lived Amazon Bedrock API key for each developer. That is a quick way to validate in-country Codex works end to end — but a long-lived credential on each developer's machine is a wider blast radius than you want for ongoing use.

Preferred production path: front Bedrock with the Bedrock Meter governance gateway and onboard developers there. In that model, developers never hold an AWS/Bedrock credential — they get a revocable, budget-capped gateway key, and the only AWS credential is a short-lived, auto-rotated ECS task role held by the gateway (not by any person). That is a much smaller blast radius, plus per-user budgets, usage metering, console onboarding, and instant revocation.

Recommendation: use this bundle to validate the Bedrock path, then set up Bedrock Meter and complete user onboarding through its admin console. See the Bedrock Meter repository and follow its installation guide: github.com/tripathihsr/bedrock-meter.

01 Challenges Addressed

Getting Codex working against Bedrock in-country, for more than one developer, involves several practical challenges this bundle is designed to simplify:

🌐

Data residency

Model traffic needs to stay within the India regions rather than reach an external SaaS or another geography.

🧩

Correct endpoint & model wiring

Small configuration details (provider name, inference-profile id, API surface) determine whether calls succeed or fail with a 404 — easy to get wrong by hand.

🔑

Per-user credentials

Each developer should have their own low-privilege identity and credential, not a shared account-wide secret.

💻

Cross-platform setup

Developers run macOS or Windows; installing Codex and writing the right config on each machine is repetitive and error-prone.

📋

Repeatable onboarding

Adding each new user — IAM user, least-privilege policy, credential, hand-off — should be a consistent, scripted sequence.

🔒

Safe secret handling

Issued tokens and key files must be stored with restrictive permissions and kept out of version control.

The question this addresses

How can an organization set up Codex against Amazon Bedrock in India — correctly and repeatably, per user, on both macOS and Windows — without hand-wiring fragile configuration or mishandling secrets?

02 How It Works

The bundle is a set of cross-platform Python scripts, driven by a single editable settings file (codex.properties). An admin provisions each user in AWS; the end user installs Codex and applies their token. The scripts auto-resolve paths and read the settings file, so most values do not need to be remembered or retyped.

⚙️

One settings file

codex.properties holds model, region, provider, auth type, and username; every script reads it.

🪪

Per-user provisioning

Creates a low-privilege IAM user and issues that user's Amazon Bedrock API key (bearer token).

🖥️

Client install & config

Installs the Codex CLI (and desktop app) and writes the exact ~/.codex/config.toml that works with Bedrock.

✅

Built-in verification

A final check confirms the full path works end to end before you rely on it.

Precedence for every setting is predictable: CLI flag > codex.properties > interactive prompt > built-in default, so you can automate or run interactively as you prefer.

04 Design Approach

The bundle separates admin provisioning from user setup, driven by one settings file, with a built-in verification at the end.

The scripts (run in order)

#ScriptWho / whereWhat it does
00_setup_admin_credentials.pyAdmin, onceStore admin AWS credentials in a named CLI profile and verify identity. Creates no resources.
11_create_codex_user_and_token.pyAdmin, per userCreate a low-privilege IAM user, attach the least-privilege Bedrock policy, and issue a bearer token (or IAM key). Saves the secret to a restricted-permission file.
22_install_codex.pyUser machineInstall the Codex CLI (and desktop app), write ~/.codex/config.toml and ~/.codex/.env, verify the CLI runs.
33_apply_token.pyUser machineWrite the bearer token into the Codex environment so it authenticates to Bedrock.
Minstall_all.pyBothMaster installer — runs the steps in sequence (--admin / --user / all), reading codex.properties.

Separation of roles

  • Admin (steps 0–1) — runs on the administrator's machine with admin AWS credentials; produces a per-user token file to hand off securely.
  • End user (steps 2–3) — runs on the developer's own machine; installs Codex and applies the token. Model, region, and provider usually stay at the validated defaults.

Guiding principle

Keep the error-prone details — the exact provider name, inference-profile id, API surface, and the least-privilege IAM policy — captured once in validated scripts and a single settings file, so each new user is a repeatable, low-risk sequence rather than manual configuration.

05 Authentication & Access Controls

Each developer authenticates to Amazon Bedrock with their own per-user credential, backed by a dedicated low-privilege IAM user. Two credential types are supported.

Credential types

  • Bearer token (recommended) — an Amazon Bedrock API key issued to the user's IAM identity. Codex reads it from ~/.codex/.env (AWS_BEARER_TOKEN_BEDROCK). The file is written with restrictive (600) permissions.
  • IAM access key — a SigV4 credential used via the AWS SDK credential chain, for teams that prefer standard IAM keys over a bearer token.

Least-privilege IAM policy

Script 1 attaches a scoped policy to each user that allows only Bedrock invocation of the India inference profile and the underlying foundation model in ap-south-1 / ap-south-2:

  • bedrock:InvokeModel* scoped to the India geographic inference-profile ARN and the foundation-model ARNs, gated by a bedrock:InferenceProfileArn condition.
  • For the bearer path, bedrock:CallWithBearerToken — Amazon Bedrock API key auth requires this action, and it does not support ARN scoping (so it is granted on *). The SigV4 / IAM-key path does not need it.

Why per-user identities matter

Each developer has a distinct IAM user and credential rather than a shared secret, so access can be granted, audited, and removed per person. Combined with the scoped policy, a user's credential is limited to invoking the configured India model — not broad Bedrock or account access.

Secret handling & the preferred credential model

  • Issued secrets are written to files with restrictive (600) permissions, and the file path is printed for a secure hand-off.
  • Token and key files (*_BEARER.txt, *_IAMKEY.txt) and the local codex.properties are excluded from version control; the admin should delete the local secret file after hand-off.
  • The per-user bearer token here is a long-lived Bedrock credential — appropriate for validation, but for ongoing use the preferred approach is short-lived credentials with a smaller blast radius: run the Bedrock Meter gateway, where the only AWS credential is a short-lived, auto-rotated ECS task role and developers hold only a revocable gateway key. See github.com/tripathihsr/bedrock-meter and complete user onboarding through its admin console.
  • For administrators, prefer AWS IAM Identity Center (SSO) over long-lived admin access keys.

06 Installation Steps

Steps 0–1 are run once by an administrator (and step 1 per new user); steps 2–3 are run by each developer on their own machine. On Windows, use python instead of python3.

Prerequisites

  • Python 3 and AWS CLI v2 on each machine
  • An admin AWS identity able to create IAM users, attach inline policies, and issue Amazon Bedrock API keys (service-specific credentials)
  • Amazon Bedrock model access enabled for the target India model in your account
  • A package installer for Codex — Homebrew on macOS, winget on Windows

  1. Edit codex.properties

    One file drives every script. Copy the template and set the values you need (model, region, provider, auth type, username). Anything left blank is prompted for or defaulted.

    cp codex.properties.template codex.properties
# then edit: username, auth_type, admin_profile (admin) / token_file (user)

  2. Admin — configure admin AWS credentials

    Stores your admin credentials in a named CLI profile and verifies identity with sts get-caller-identity. Creates no AWS resources.

    python3 0_setup_admin_credentials.py

  3. Admin — create the user and issue a token

    Creates the low-privilege IAM user codex-bedrock-user-<name>, attaches the scoped Bedrock policy, and issues the credential. It prints exactly what it will create and asks for confirmation first.

    # bearer token (recommended)
python3 1_create_codex_user_and_token.py --user alice --type bearer

# or an IAM access key instead
python3 1_create_codex_user_and_token.py --user alice --type iamkey

    The secret is saved to a 600-permission file (path printed). Hand it to the user securely and delete the local copy afterwards; never commit it. IAM changes can take ~30s to propagate.

  4. User — install Codex and write config

    Installs the Codex CLI (and desktop app) and writes ~/.codex/config.toml and ~/.codex/.env resolved to the current user's home. It verifies the CLI actually runs — do not continue until that check passes.

    python3 2_install_codex.py

  5. User — apply the bearer token

    Writes the token into the Codex environment so it authenticates to Bedrock.

    python3 3_apply_token.py --token-file /path/to/codex-bedrock-user-alice_BEARER.txt

    On Windows, fully restart the Codex desktop app afterwards. On macOS, open a new terminal so the environment loads.

  6. Verify

    Confirm the full path works. The unset ensures the bearer token is used rather than a leftover SDK profile.

    unset AWS_PROFILE AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
codex exec --skip-git-repo-check "reply with exactly: BEDROCK OK"
# Expected: BEDROCK OK  (ignore the harmless "Model metadata not found" warning)

One-shot install (optional)

After editing codex.properties, the master installer can run the steps for you — all of them, or just the admin or user subset — reading the settings file and stopping on the first failure with a resume hint.

python3 install_all.py            # interactive menu (pick steps)
python3 install_all.py --admin    # admin steps only (0,1)
python3 install_all.py --user     # user steps only (2,3)
python3 install_all.py --dry-run  # print the sequence without executing

Key configuration detail

The provider name is the make-or-break setting: use model_provider = "amazon-bedrock-runtime". The older amazon-bedrock value targets a different endpoint and returns a 404 model does not exist for the India inference profile.

07 Summary

This bundle makes "run Codex against Amazon Bedrock in India" a repeatable, per-user setup rather than manual configuration. An admin provisions each developer's low-privilege identity and token; the developer installs Codex and applies the token; a built-in check confirms the path works.
